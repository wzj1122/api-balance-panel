## 四、功能性优化建议

### 性能

- **P1 config.json 写盘过于频繁**：`query.ts:185` 每查完一个账号就 `store.updateLastResult → save()`（`store.ts:437-446` → `:304-323`：copyFileSync 备份 + 写 tmp + fsync + rename）。N 个账号一轮刷新 = N 次全量序列化 + N 次 `.bak` 复制；`bumpNotice`（`:532-539`）同理。**建议**：内存脏标记 + 500ms~1s 防抖批量落盘；`.bak` 改为每会话/每小时轮换一次而非每次写都复制。
- **P2 缓存命中行重复写快照**：`query.ts:231` 把 `{...cached.row, cached: true}` 补进 rows、非 force 时 `queryAccount` 直接返回缓存行（`:100-104`），这些行照常进 `snapshot.append(rows)`（`:239`）→ 同一 `ts` 的重复快照每轮刷新都落盘，snapshots.json 虚增，充值/闪断识别边界变糊。**建议**：append 时跳过 `cached:true` 或按 `(account_id, ts)` 去重。
- **P3 刷新补齐路径串行 await**：`query.ts:229-233` 对缓存冷账号逐个 `await queryAccount`，应并入已有的 `runPool` 并行。
- **P4 监控真实调用串行 + 历史全量重写**：`monitor.ts:226-231`、`:244-254` for 循环逐个 `await runCheck`；每条 check 触发 `saveHistory()` 全量重写（`:72-80`，最多 6000 条 JSON）。**建议**：`runPool` 并发 + 仿 `snapshot.ts:144-150` 节流落盘。
- **P5 Key 管理重复解密全量密钥**：`keys.ts:20` `toKeyRow` 对每账号 `revealSecret`（只为算 `hasSecret`，其实 `!!acc.secret_enc` 即可——`toVaultRow:53` 就是这么做的）、审计④又解密一次（`:129`）、`vaultFingerprint` 再解密（`keyvault.ts:128-132`）；审计②对每行 `snaps.filter`（`:95`）O(账号×快照)。**建议**：hasSecret 改判密文、快照按 account_id 预分组、审计解密一次。
- **P6 `applyCorrections` 每次全量 map**：`corrections.ts:146-181` 对全部快照 O(n×校正数) 变换，`keys/notify/usage` 各自再调一遍 `readSnapshots()`。快照近万条时可观。**建议**：按账号预分组 + 短 TTL 结果缓存。

### 健壮性

- **R1 退出丢快照（数据丢失风险，最高优先）**：`snapshot.flush` 有 1s 节流（`snapshot.ts:144-150`），而 `index.ts:125-132` `before-quit` **没有调用 `snapshot.flush()`**，退出瞬间未落盘的快照直接丢；且 `flush` 的 `writing` 旗标（`:154`）会让"写盘进行中再触发的 flush"被静默丢弃且不再重排，极端时序下最后一批快照悬空。**建议**：`before-quit` 里 `await snapshot.flush()`；`writing` 挡掉时置 dirty 稍后重排。
- **R2 续期竞态**：`renewForAccount`（`query.ts:69-92`）无 in-flight 去重——保活（5 分钟）、查询前临期检查（`:117-121`）、401 重试（`:134`）、手动按钮可并发触发多次 `renewCredential`，每次都开隐藏窗口并读写**同一分区** Cookie（`renewal.ts:187-206`）→ 互相覆盖会话；冷却 `renewCooldown` 只在失败后设置。**建议**：同账号续期互斥（in-flight Map）。
- **R3 `loadURL` 未处理 rejection**：`window.ts:103-105` `void win.loadURL(...)` 无 `.catch`，加载失败的 rejection 只落到全局 `unhandledRejection`（`index.ts:44-46`）一行日志，主窗口可能停在空白页。**建议**：补 `.catch` + 错误提示页。
- **R4 旁路数据文件损坏即静默清零**：`keyvault.ts:44-53` 读 `keys.json` 失败直接当空表，下次 `save()` 就把损坏文件覆盖（Key 库无声丢失）；`monitor.ts:36-45,61-70` 同理。config.json 有"归档坏文件 + 回滚 .bak"三件套（`store.ts:260-275`），这几处没有。**建议**：损坏时先改名归档再重建。
- **R5 `saveAccount` 不保留 `deleted_at`**：`store.ts:368-380` 重建对象时未拷贝该字段，回收站里的账号被编辑保存会"复活"。**建议**：保留 `deleted_at`（及未知自定义字段）。
- **R6 返回形状类型不一致**：`ipc.ts:103-110` `ACCOUNT_REMOVE` 返回裸 `boolean`，而 `shared/ipc.ts:149` 声明 `Promise<{ ok: boolean }>`——渲染端按对象解构会拿到 `undefined`。**建议**：统一返回 `{ ok }`。
- **R7 `runPool` 结果顺序不定**：`runPool.ts:15` 按完成序 `push`，`refresh` 的 rows 每次顺序不同（`query.ts:219-222`），渲染端整表替换会导致卡片顺序逐轮跳动。**建议**：按 targets 原序回填结果。
- **R8 异常吞掉不留痕**：`bgstore.ts:100-102`（removeBackground 静默 false）、`keyvault.ts:60-62`（保存失败仅 warn，用户以为已保存）、`aliyun.ts:269-271`（节省计划 catch{}）等。**建议**：至少补 logger。
- **R9 `exportLogs` 不含磁盘日志**：`logger.ts:156-176` 只导出内存 buffer（≤3000 条），与注释"缓冲 + 磁盘日志合并"不符，排障会误以为拿到了全量。**建议**：实现与注释二选一对齐。
- **R10 `activeDays` 口径 bug（叠加死代码）**：`usage.ts:966-977` 每个单位的 `activeDays` 实际统计"所有单位"有消耗的天数（`flows.byDay` 未按单位过滤），单位明细里的活跃天数会虚高。**建议**：按单位过滤 byDay，顺手删掉死的 `perDay`。
- **R11 校正影响条数忽略 `toTs`**：`ipc.ts:396` `affected[c.id] = raw.filter((s) => s.ts >= c.fromTs).length`，"只改一天"的校正在界面上会显示影响了之后全部快照。**建议**：加上 `s.ts < c.toTs` 条件。
- **R12 监控请求绕过 ASCII 预检**：`monitor.ts:193-198` 直接 `fetch`，用户在监控表单头里粘中文只会得到难懂的 fetch 报错，而不是 `BAD_HEADER` 人话（`http.ts:39-49` 的预检被绕开）。
